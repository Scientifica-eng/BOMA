# BOMA Terminology Registry

**Status:** Living document — Cycle 001

**Purpose:** Establish a controlled vocabulary for BOMA before the experimental development expands. BOMA terminology is primary; proof-assistant terminology is a backend vocabulary and must not silently redefine BOMA concepts.

## 1. Terminological Independence Principle

BOMA defines its own architectural concepts independently of any proof assistant. Lean, Coq, Isabelle, Agda, or another verifier may provide an implementation vocabulary, but a backend term is not a BOMA term merely because it is convenient for implementation.

A BOMA concept shall be mapped to a backend concept only after its semantic role has been examined.

## 2. Layers

### BOMA-Core
Concepts that belong to the architecture itself.

### Backend
Terms supplied by a particular proof assistant or formalization environment.

### Mapping Registry
Explicit relations between BOMA concepts and backend constructs.

## 3. Mapping Types

- **Equivalent** — sufficiently strong semantic correspondence for the stated scope.
- **Approximate** — related concepts, but not semantically identical.
- **Implemented-by** — a BOMA concept is represented using one or more backend constructs.
- **Composed-of** — one BOMA unit corresponds to several backend entities.
- **No-counterpart** — the backend has no native concept with the required BOMA meaning.
- **Backend-specific** — a backend concept that must not be promoted to BOMA-Core without explicit architectural justification.

## 4. Initial BOMA Vocabulary

| BOMA term | Working definition | Backend status | Mapping |
|---|---|---|---|
| **Brick** | Smallest independently identifiable unit of foundational content at the chosen architectural analysis level. | No exact Lean counterpart. | Implemented-by / Composed-of |
| **Block** | Optional grouping of Bricks that has a useful structural or semantic identity. | No exact Lean counterpart. | Composed-of |
| **Dependency** | An explicit relation indicating that one architectural unit relies on another. | Lean has declaration dependencies/references. | Approximate / Implemented-by |
| **Decision Point** | A location at which alternative admissible developments can be distinguished. | No native Lean architectural counterpart. | No-counterpart |
| **Branch** | A distinct development produced by selecting an alternative at a Decision Point. | May be represented with namespaces, files, modules, commits, or separate environments. | Implemented-by |
| **Injection** | Introduction of content or assumptions into a development that was not already available from its prior dependency closure. | May involve declarations, axioms, imports, or environment changes. | Implemented-by |
| **Minimal Injection** | Introduction of no more foundational content than is required for the intended development step. | No native Lean counterpart. | No-counterpart |
| **Verification** | Evaluation of whether a stated formal object satisfies the applicable verification criteria. | Kernel checking is one backend mechanism, not the full BOMA concept. | Approximate |
| **Correction** | Controlled modification made in response to a Check finding. | No native Lean counterpart. | No-counterpart |
| **Development** | An ordered and dependency-structured construction of foundational content. | Can be represented by declarations/environment history. | Implemented-by |
| **Foundational Space** | The space of admissible developments and branches generated by architectural alternatives. | No native Lean counterpart. | No-counterpart |

## 5. Initial Lean Backend Vocabulary

These terms are recorded as Lean/backend terminology, not as BOMA architectural concepts.

| Lean/backend term | Role in Lean | BOMA relation | Caution |
|---|---|---|---|
| **declaration** | A named formal declaration entered into the environment. | Possible implementation unit for a Brick. | Do not equate declaration with Brick. |
| **definition** | A declaration introducing a definitional object, commonly via `def`. | Possible Brick implementation. | BOMA Brick may require more than one declaration. |
| **theorem** | A declaration whose type expresses a proposition and whose value/proof establishes it. | Possible Brick implementation. | Do not equate theorem with BOMA Proof or Brick universally. |
| **lemma** | Common Lean naming/category convention for an auxiliary theorem. | Possible Brick implementation. | Primarily a role/naming convention, not a BOMA category. |
| **axiom** | A declaration accepted without a proof term supplied in Lean. | Possible representation of an injected foundational assumption. | Must be distinguished from BOMA Assumption/Injection. |
| **proposition** | A type that can be inhabited by proofs and is used to state a logical claim. | Backend logical object. | Not automatically a Brick. |
| **type** | Core Lean notion used to classify terms. | Backend concept. | Not equivalent to BOMA Block or Brick. |
| **term** | A formal expression inhabiting a type. | Backend representation. | Too broad to serve as a BOMA unit without additional criteria. |
| **proof term** | A term that inhabits a proposition. | Backend representation of a proof. | BOMA Proof may include architectural metadata beyond the term. |
| **environment** | The collection of declarations and related information available to Lean. | Possible backend representation of a development state. | Not equivalent to BOMA Development. |
| **import** | Makes declarations from another module available. | Possible implementation mechanism for dependency/injection. | Importing is not itself necessarily a BOMA Injection. |
| **namespace** | Organizes names and declarations. | Possible representation aid for a Block or Branch. | Organizational only unless BOMA semantics are added. |
| **module** | Lean source/module organization and compilation unit. | Possible representation of a Block or Branch. | Backend-specific. |
| **elaboration** | Converts surface syntax into elaborated formal terms, resolving implicit information and notation. | Backend process. | Not a BOMA construction step by itself. |
| **kernel** | Trusted core that checks the correctness of accepted formal objects. | Backend verification mechanism. | Do not equate kernel checking with all BOMA Verification. |
| **tactic** | A proof-construction/programming mechanism used to generate proof terms. | Backend method. | A tactic is not a BOMA Proof. |
| **instance** | A declaration used by type-class inference and related mechanisms. | Backend-specific unless a BOMA experiment gives it architectural significance. | Do not promote automatically to Core. |

## 6. Non-Conflation Rules

1. **Brick ≠ declaration.** A Brick may be represented by one declaration, several declarations, or a combination of formal and architectural records.
2. **Block ≠ namespace/module.** A Block is a BOMA grouping; namespaces and modules are possible backend representations.
3. **Decision Point ≠ choice of syntax or tactic.** It concerns an architectural alternative, not merely an implementation convenience.
4. **Branch ≠ Git branch or Lean namespace.** These may represent a Branch operationally, but they are not semantically identical.
5. **Verification ≠ kernel checking.** Kernel checking is evidence/mechanism supplied by a backend; BOMA Verification includes the applicable architectural verification criteria.
6. **Injection ≠ import.** An import is a backend mechanism. Whether it constitutes a BOMA Injection depends on the dependency and availability state of the development.
7. **Proof ≠ proof term.** A proof term is a backend artifact; BOMA may attach provenance, dependencies, verification status, and architectural context.
8. **Assumption ≠ axiom.** An assumption may be represented in several ways depending on the experimental design.

## 9. Evidence Status

Every terminology decision should carry one of these statuses:

- **Proposed** — introduced as a working hypothesis.
- **Observed** — supported by a laboratory observation.
- **Validated** — survived a defined Check criterion.
- **Corrected** — modified after a detected deficiency.
- **Deprecated** — retained for historical traceability but no longer recommended.
- **Normative** — accepted as part of the BOMA specification after sufficient evidence.

## 10. Cycle 001 Rule

The laboratory shall prefer discovering missing distinctions over prematurely expanding the vocabulary. When Lean terminology has no exact BOMA counterpart, the terms remain explicitly separated rather than being forced into a one-to-one translation.

The next PDCA cycle may revise this registry using recorded observations from Cycle 001.
