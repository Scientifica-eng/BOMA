# REVERSE-003 — Decomposing the Closure Requirement

**Path:** `REVERSE-001`  
**Status:** Provisional result

## 1. Intention / Goal

Determine whether the closure/induction component of the natural-number structure is itself a primitive requirement, or whether it can be reduced to simpler structural conditions.

## 2. Starting Observation

A successor-like relation plus an initial point is insufficient to distinguish the natural numbers from a finite truncated chain.

We therefore require some additional condition preventing the domain from ending merely because the explicitly displayed construction ended.

## 3. Experiment A — Treat Closure as a Primitive

Assume a rule of the form:

> Anything generated from the initial stage by repeated allowed extension belongs to the intended domain, and nothing outside the generated structure is admitted without justification.

This immediately solves the truncation problem at the level of specification.

However, it introduces a global membership/domain condition. It is therefore a legitimate candidate primitive, but it is not obviously more primitive than the numerical structure itself.

## 4. Experiment B — Treat Closure as a Derived Consequence of Construction

Try to obtain closure merely from the local transition rule:

```text
s₀ → s₁ → s₂ → ...
```

No local transition rule by itself specifies which additional objects count as members of the domain, nor does it rule out a prematurely truncated domain.

Thus closure is not recoverable from local successor information alone.

## 5. Experiment C — Treat Closure as a Rule About Admissible Construction Histories

Instead of defining a domain first, define the admissible structure through a rule:

> The construction may continue by the same extension protocol whenever the current state is an admissible constructed state.

This does not yet produce a completed infinite object. It gives an **open generative protocol**.

The distinction is important:

```text
open generative protocol
        ≠
completed infinite domain
```

The protocol says what further construction is permitted; it does not claim that all permitted outcomes exist simultaneously as one completed object.

## 6. Result

Closure decomposes into at least two different ideas:

### Local generativity

Given an admissible state, the extension rule specifies a legitimate next construction.

### Global admissibility

The intended domain is restricted to what is generated by the initial condition and the admissible extension protocol.

These are not the same statement.

The reverse analysis therefore suggests that "induction" in a standard presentation may package together a constructional generativity principle and a domain-generation principle.

## 7. Decision

Do not treat mathematical induction as the primitive starting point of the project.

Instead, preserve two candidate layers:

```text
L1: open generative rule
L2: generated-domain principle
```

The project should determine later whether L2 can be derived from the chosen notion of construction, whether it must be stipulated, or whether a weaker fixed-point/minimality principle suffices.

## 8. Consequence for the Forward Path

The forward path should not try to manufacture "induction" as an ordinary Brick before a candidate domain exists.

A more promising route is:

```text
construction protocol
       ↓
admissible generated structures
       ↓
minimal/closed generated domain
       ↓
only then identify the resulting structure with N
```

This avoids inserting the full induction principle into the pre-mathematical foundation prematurely.

## 9. Open Question

Can the phrase "minimal generated domain" itself be stated without importing set theory, quantification over all subsets, or an already completed mathematical universe?

That question is now a more promising reverse-engineering target than simply asking how to encode induction.
